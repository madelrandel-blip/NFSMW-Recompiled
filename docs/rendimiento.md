# Performance

Measured, not assumed. The reference machine is modest on purpose: if something is
noticeable there, it's noticeable anywhere.

**Reference machine:** Intel Iris 540 (integrated, vendor 0x8086, device 0x1926), few
cores. The SDK warns at startup: `Too few processor cores - scheduling will be wonky`.

What the GPU reports, and what conditions everything else:

```
Max GPU virtual address bits per resource: 38
Rasterizer-ordered views: yes
Resource binding: tier 3
Tiled resources: tier 3
Pixel-shader-specified stencil reference: yes
```

## The biggest difference: the EDRAM path

| Path | What it does | Measured FPS |
|---|---|---|
| ROV | Rasterizer ordered views. Exact | ~10 |
| RTV | Host render targets. Approximate | ~18 |

Almost double. The SDK picks ROV on Intel by default, which is the conservative
decision; `render_target_path_d3d12 = "rtv"` bypasses it.

**The cost:** on some integrated GPUs the fast path leaves a strange horizontal band.
It's not fully closed — see [problemas-conocidos.md](problemas-conocidos.md).

This setting is `kInitOnly`: it's decided at startup and can't be touched from F4. The
launcher passes it on the command line.

## Internal resolution

`--resolution_scale` is the emulators' "x2": it multiplies the size of the render targets
and the emulated EDRAM, so the game really does draw more pixels.

It grows with the square: x2 is **four** times the pixels. Starting from 18–38 fps at x1,
on this machine x2 isn't playable.

What is worth knowing is that **it won't be cut back for lack of capability**. The SDK
limits it in two cases:

- if the GPU is below *tiled resources tier 1* — here it's tier 3
- if the address space isn't enough: `kBufferSize × scale²` has to fit in the bits per
  resource. With 38 bits and a 512 MB buffer, at x2 it needs 31. That's plenty of
  headroom.

If the SDK does cut it back, it says so:

```
The requested draw resolution scale is not supported by the device or the emulator,
reducing to NxN
```

Don't confuse this with `--resolution`, which only changes the window size and the guest
video mode. See [arquitectura.md](arquitectura.md).

## Settings that cost and sometimes don't show

### `readback_resolve`

Default `none`. The value `fast` copies from GPU to CPU **every frame**.

The application itself (`nfsmw_app.h`) sets it because without it the image comes out
washed out and the sun blown out. In other words: it's a visual fix, not a preference,
and its cost is the price of it looking right.

### `native_stencil_value_output_d3d12_intel`

**Leave it off on Intel.** The SDK excludes this path on Intel on purpose:

```cpp
use_stencil_reference_output_ =
    REXCVAR_GET(native_stencil_value_output) &&
    provider.IsPSSpecifiedStencilReferenceSupported() &&
    (REXCVAR_GET(native_stencil_value_output_d3d12_intel) ||
     provider.GetAdapterVendorID() != kIntel);
```

Turning it on forces that output on Intel, which is exactly the excluded case. With the
RTV path it wrecks the render **without giving a single GPU error**, which makes it
especially hard to diagnose.

### `d3d12_tessellation_wireframe`

Debug switch: draws all tessellated geometry as wireframe. Don't touch it unless
debugging.

These last two once slipped into `nfsmw.toml` from the F4 menu and produced a broken
green screen that looked like a graphics backend bug. **If it suddenly looks wrong,
check the toml before suspecting the code.**

## Frames

Neither vsync nor the fps limit works out of the box: `parche_presentador.py` implements
them. See [parches.md](parches.md).

A detail that surprises people: **limiting the fps doesn't slow the game down.** The
guest's vertical blanking is generated by a separate thread against the wall clock, at
`video_mode.refresh_rate` (60 Hz), independent of the drawing rate. If you want to change
the game speed, that's `game_speed`, a different setting.

## The shader cache

It lives in `%USERPROFILE%\Documents\nfsmw\cache`, **outside** the portable folder. It
comes from `GetUserFolder() / GetName()`, and `GetName()` is in the code, so renaming the
executable doesn't move it.

Two consequences:

- Rebuilding `build\` doesn't delete it. The first boot after a new build is still fast.
- If you suspect the cache is corrupt after switching backends, you have to delete it by
  hand.

On a normal boot you see lines like `Translated 85 shaders from the storage` and
`Created 258 graphics pipelines ... from the storage`.

## Method

The numbers above came from comparing runs changing **one** thing at a time and watching
the F3 counter. It's crude but enough for 80% differences.

It's no good for small differences: the run-to-run variability on an integrated GPU with
few cores swallows any single-digit improvement.

# Architecture

How the pieces fit together, and above all **where everything lives**, which is what's
hardest to understand when you arrive at the project.

## The three layers

```
   YOUR ISO
     │  EXTRAER_XEX.bat
     ▼
   default.xex ──────────┐
                         │  rexglue codegen
                         ▼
                   app/generated/          131 files of generated C++
                   nfsmw_recomp.*.cpp      the game's PowerPC code, translated
                   nfsmw_register.cpp      address → function table
                         │
                         │  clang
                         ▼
                   ┌───────────────┐
                   │  nfsmw.exe    │  the game. Its code is in here.
                   └───────┬───────┘
                           │  links against
                   ┌───────▼────────────────────────────┐
                   │  rexruntime.dll   (the SDK)        │  ← THE FIXES LIVE HERE
                   │  kernel, VFS, audio, input, window │
                   └───────┬────────────────────────────┘
                           │  loads at runtime (LoadLibrary)
                   ┌───────▼────────────────────────────┐
                   │  rexgpu-xenos.dll                  │
                   │  Xenos → Direct3D 12 / Vulkan      │
                   └────────────────────────────────────┘
```

## What you need to understand before touching anything

**Almost none of this project's fixes live in this repository.**

The game's code can't be edited: it comes out of the generator and gets overwritten on
every `codegen`. And the bugs we've been fixing —the audio hang, the vsync that didn't
exist, the API selector, the privileges gate— aren't the game's: they're the SDK's.
They end up compiled inside `rexruntime.dll`.

That's why the build does, in this order:

1. Applies the patches to the **SDK source**, which is in `..\rexglue-sdk`
2. Rebuilds the SDK
3. Generates the game's C++
4. Builds the game
5. Assembles the portable folder

If you skip steps 1 and 2, you build a perfect game against an unpatched runtime, and
the audio dies just like the first day.

## What's in each place

### `app/`

The application. It's surprisingly small, and that's a good sign.

| File | What it is |
|---|---|
| `nfsmw_manifest.toml` | What the generator reads: where the XEX is, where to write, which TOMLs to include |
| `overrides.toml` | Hand-written corrections to the generator, each with its reason |
| `huecos.toml` | 774 gaps of ≥8 bytes that the automatic analysis didn't recognize as code. Generated by `HUECOS.bat` |
| `nfsmw.toml` | Game config that gets copied to the portable folder |
| `src/main.cpp` | Four lines: starts the app |
| `src/nfsmw_app.h` | The `ReXApp` subclass. This one does have game-specific logic |

`nfsmw_app.h` deserves a read. It does two things that aren't obvious:

- **It finds the ISO by itself**, so opening the executable with no arguments works.
  It prefers the one named the same as the executable, otherwise the first
  alphabetically, and otherwise a `game_root\` folder. This runs **before**
  `nfsmw.toml` is read, so setting `game_data_root` in the toml does nothing: the
  command line wins and, if there isn't one, this does.
- **It sets mandatory settings** without which the game either doesn't show or can't
  be controlled: `gpu_plugin`, `mnk_mode` and `readback_resolve`. It only sets them if
  nobody asked for them, so the command line and the toml still win. And they're in
  two different places on purpose: `readback_resolve` is registered by the GPU plugin,
  which loads later, so setting it earlier would be writing to a flag that doesn't
  exist yet.

### `tools/parche_*.py`

The patches. Each is a script that applies and reverts by exact text substitution on
the SDK source. See [parches.md](parches.md) for the catalog and the reasoning behind
the design.

### `tools/lanzador/`

The launcher, in C# with WinForms. It builds with the `csc.exe` Windows already
ships, with nothing to install. See [lanzador.md](lanzador.md).

### `tools/diagnostico/`

Instrumentation. It doesn't go into a normal build. It's applied by hand when you need
to investigate something and reverted afterwards.

## The cvar system, which is how everything is configured

The SDK has a configuration variable registry. Understanding its two axes saves hours.

**Source priority**, from lowest to highest:

```
kDefault  <  kConfig  <  kEnvironment  <  kCommandLine  <  kRuntime
```

A value set on the command line beats the one in `nfsmw.toml`. That's not a detail:
it's what makes the launcher an escape hatch. If you pick a graphics API that gives
you a black screen on your machine and it gets saved to the toml, the launcher can get
you out of there because it always passes `--gpu_backend`.

**Lifecycle**, which decides when it can be changed:

| Lifecycle | Means |
|---|---|
| `kHotReload` | Can be changed on the fly and takes effect immediately |
| `kRequiresRestart` | Can be changed and is saved, but doesn't apply until restart |
| `kInitOnly` | **Can't even be saved** after startup |

The difference between the last two cost a while. `kInitOnly` makes the F4 menu draw
the setting in red and disabled: you can see it but not touch it. If what you want is
"can be changed, but needs a restart", that's `kRequiresRestart`, which also makes the
SDK note it in its pending-changes list.

A warning about that list: `SetFlagFromSource` records any `kRequiresRestart` that
gets touched, **without looking at where the value comes from**. So a `--gpu_backend`
on the command line, which is already applied from startup, would still enter it and
the menu would open saying "restart needed" from the first second. That's why
`parche_backend.py` clears the list once startup finishes.

## The guest clock

`Clock::set_guest_time_scalar()` scales the guest clock **as a whole**: the tick
counter, system time, timers and waits. That's why it works as a game speed control
without touching anything else — the thread that generates vertical blanking compares
guest ticks, so it adjusts itself.

With one caveat: `RecomputeGuestTickScalar` does `frac.second *= uint64_t(10.0 /
escala)` when the scale is ≤ 1.0. With the scale at zero that's `10.0/0.0` = infinity,
and converting infinity to `uint64_t` is undefined behavior. That's why the launcher's
0% stays at one thousandth of normal speed instead of zero.

## Two resolutions that aren't the same

This confuses everyone, including whoever is writing this.

- `--resolution` changes the **guest video mode** and the window size. It doesn't ask
  the game to draw finer. Most Wanted draws into its own fixed-size render targets and
  lets the scaler stretch the result. Raising this enlarges the image.
- `--resolution_scale` multiplies the size of those render targets and the emulated
  EDRAM. **This** is the emulators' "x2". It's expensive and grows with the square.

See [rendimiento.md](rendimiento.md) for the measured numbers.

## EDRAM, which is where half the performance comes from

The Xbox 360 doesn't have normal render targets: it has 10 MB of embedded memory where
fixed-function hardware does blending and depth testing. Emulating that has two paths:

| Path | How | Cost |
|---|---|---|
| ROV | Rasterizer ordered views. Exact | Slow |
| RTV | Host render targets. Approximate | Fast |

On the measured Iris 540, going from ROV to RTV took the game from ~10 to ~18 fps. The
SDK picks ROV on Intel by default, which is the conservative decision;
`render_target_path_d3d12` lets you bypass it.
